# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`file-tree` is a Claude Code plugin (a "mod") that opens a project file tree and file preview in a pane. It is not a Node package: there is no `package.json`, no bundler and no build step. Claude Code loads `hooks/register.tsx` directly, via `hooks/hooks.json` (`{ "modules": ["./register.tsx"] }`).

There are no fixtures in the repo. To try the pane by hand, build a scratch folder outside it with many files, deep folders, a very long name, CJK/emoji names, a symlink and a dangling one, a `chmod 000` file, a >4 MiB text file, a binary, a png/jpg, an mp4 and a fifo.

## Commands

- Type-check: `tsc -p tsconfig.json` (no emit). `tsconfig.json` extends `.claude-plugin/types/tsconfig.json`, which is strict, uses `noUncheckedIndexedAccess`, and compiles `hooks/`, `types/` and `tests/` with a `h`/`Fragment` JSX factory.
- Tests: `claude plugin test <plugin folder>` runs `tests/file-tree.test.ts` against the engine (the kit is `claude-code/testing`). Also run `claude plugin validate <plugin folder>`, which checks the manifest, the `PluginState` contract and the hooks' calls. A new `atom` missing from `types/index.d.ts` fails validation.
- Run it: `claude --plugin-dir <plugin folder>` (the folder hot-reloads on edit). The pane opens on `session.start`, or with `/tree`. Per the status line, `ctrl+x Tab` enters the pane and `Esc` returns.
- Layout: the fullscreen layout (the default in 2.1.302; `CLAUDE_CODE_NO_FLICKER=0` turns it off) docks the pane on the right from 110 columns, and both opens ask the dock for `DOCK_COLUMNS`. With it off the pane renders inline above the prompt as a short block. The unasked open in `session.start` was seen placed at 120 columns.
- Edit and test from two sessions. A session started with `--plugin-dir` pointing here cannot Write/Edit this folder under auto mode (the classifier will not judge an agent editing its own loaded plugin), so edit from a plain `claude` session and test from a second one started with `--plugin-dir` in the folder whose tree you want to see.

## Layout

- `hooks/register.tsx`: the whole plugin, one `register` export that attaches hooks with `on(...)`, plus `loadText` at the bottom.
- `types/index.d.ts`: augments `PluginState` with the shape of the plugin's four atoms. Add a field here whenever a new `atom` is added.
- `.claude-plugin/plugin.json`: manifest. `.claude-plugin/types/` holds the engine's type declarations (`claude-code`, `claude-code-tools`, `claude-code-mcp`) and is gitignored by its own `.gitignore` (`*`). Treat it as generated reference material; grep it for the real API (`$.fs`, `$.process`, `$.ui`, hook event names) rather than guessing.

## Architecture

State is split between engine atoms and module-level variables, and the split matters:

- Atoms (`expanded`, `selected`, `cursor`, `tick`) are session state (`$.state`, not kept across sessions) read with `read($, atom)` and changed with `update($, atom, fn)`. Updating any of them re-triggers the `ui.render` hook. `tick` is only a redraw counter: bump it to force a render (after any `tool.call`, and on preview scroll). The module's `at` is the cursor's source of truth; the render reads the `cursor` atom every time (so a write redraws) but adopts it only once after a module load, because mid-burst of wheel ticks it returns the write before last and would pull the cursor back.
- Module variables (`order`, `at`, `shown`, the per-surface windows in `geos`, and the `loaded`/`sizes`/`pngs` caches) mirror what the last render drew. Hooks outside render use them so they can act without a redraw. `ui.scroll` reads `order`/`at` to move the cursor, and finds its surface's window in `geos` by `bodyRows` (the event names no surface) to tell a wheel over the preview box (`previewFrom`) from one over the tree. The caches are keyed by path, mtime and size and keep only their newest few entries.

Hooks:

- `ui.render` (`component: 'Pane'`) rebuilds everything each time: walks the tree through `$.fs.list` honoring the `expanded` set, wraps names to the pane width, stats the selected file, picks image vs text vs "opaque" preview, then lays out hint line, tree window and preview box inside the pane's `bodyRows`. The tree gets whatever height the preview box leaves. Renders run one at a time (the `drawing` chain): a slow one (an image through `sips`) finishing after a newer one left the engine holding buttons it no longer drew, and presses on them did nothing (the debug log says "no Button … is held under handle"). Under 14 columns no box is drawn and nothing is read. Image work (`sips` size, then PNG) runs beside the renders in `measure`, with timeouts; the box says "measuring…" until it lands and a `tick` redraws, so a slow `sips` (an iCloud file downloading) holds up neither the arrows nor presses.
- `ui.scroll` is how the arrow keys and wheel work. The engine scrolls a focused pane itself, so the render appends a padding row to keep the body taller than the pane, which is what makes arrow keys reach this hook. Keep that padding when editing the layout: every row the layout counts must be drawn (tree rows are clipped to the window, the image sits in a `Box` of fixed height because the engine draws its alt on one line), so the body is exactly `bodyRows + 1`. When it is not, the arrows move the engine's own focus instead and Enter presses the wrong row. Home and End arrive as `by = ±contentRows` with no pointer and jump to the ends.
- `ui.focus` makes the cursor follow the engine's focus ring when the person moves it onto a row (Tab, click), so Enter and `›` agree. `focusCursor` moves the ring the other way after a scroll and retries a refused move. With a text preview taller than its box open (`scrollable`), Tab from the tree puts the keys in the preview (`inPreview`): the hook sends the ring to the box title (`close-preview`) and the arrows, Home/End and the wheel scroll the file; any other move of the ring sends it back to the cursor's row. In a real session a click raises no person `ui.focus` at all, only the press, so every person move is a Tab; the row presses (`pick`) and scrollbar or jump presses (`jump`) set the mode themselves. A Tab toward one of the engine's own stops (the pane's ✕) cannot be redirected (`next` refuses an element there), so the hook keeps the ring and moves it back to the row itself. The pane draws no ring after Esc and re-entry, so a keyboard scroll in the preview puts it back on the title. Esc is the engine's (it hands the keys back to the prompt), so the mode survives it.
- `tool.call` redraws after any tool, since it may have changed the files on disk.
- `session.start` registers `/tree` and opens the pane; `command.run` reopens it.

Layout arithmetic is cell-based, not character-based. Wide (CJK, emoji) characters take two columns and combining marks none (`WIDE`, `cells`, `chunk`, `fit`). Tree rows can span several lines, so the visible window counts cells (`cum`, `span`). Control characters and lone surrogates are replaced before reaching `Text`/`Code` (`clean`, `cleanName`), which reject them.

Preview rules in `loadText` and the render body:

- Only regular files are read; pipes and devices are never opened because they can block. Images are only sent to `sips` if `stat` says `file`.
- Text reads stop at 4 MiB (`READ_MAX`, the engine's limit for `$.fs.read` and process stdout); bigger files are read with `head -c` and the footer says "cut". Extensions in `OPAQUE` skip the read.
- The text box wraps long lines inside the box (`wrapLine`: at the last space that leaves a row half full, else mid-word, with continuation rows indented past the line's indent) behind the plugin's own line-number gutter, which numbers only a line's first row. The window scrolls by drawn rows; the range names file lines. Each surface's window also keeps its top row as a place in the file (`anchor`: line and offset), so a resize, which re-wraps every line, reopens the window on the same place. `Code` highlights each row on its own, so `scan` follows /* */ comments, JS template literals and regexes, Go raw strings and Python triple quotes, and a row that starts inside a comment or string is drawn as plain `Text` (dim for a comment) between `Code` runs. Rows are wrapped per width and cached (`wraps`), so a drawing never nears the engine's 100,000-character cut. PageUp/PageDown scroll an open text preview by its height. A file taller than its box gets a scrollbar in the box's last column (`bar`, one `plain` Button per row keyed `sb-<i>`), which takes that column from the text; a press on a cell opens the file that far down. It is drawn only on the terminal (a desktop draws a plain Button as a native button) and only with room for three cells. Whether a file overflows is found by `overflows` without a second full layout (a minified file paid one per wheel tick).
- Images go through macOS `sips` in the background (size query, then PNG downscale through 900/600/400/256/128 px until under the 2 MiB `IMAGE_MAX`). Open and reveal buttons try `open`/`xdg-open`/`explorer` in turn (never `cmd /c start`, which re-parses the name, so `a&calc` would run calc), so the non-image paths are meant to stay cross-platform while image preview is macOS-only.
- Row buttons are keyed with `rowKey` (`encodeURIComponent` of the path, with lone surrogates spelled out first because `encodeURIComponent` throws on them) so names never collide with fixed button keys like `close-preview`.
- OS refusals come back from the engine as text with no `code`; `errno` pulls the `E…` token (for example `EACCES`) out of the message for the box.
- The cursor row is underlined as well as marked with `›`. The engine inverts whichever row rests under the mouse pointer (hover) and re-applies it after every relayout, so after closing a preview the highlight lands on the row now under a stationary pointer while the cursor stays put. That is the engine's behaviour and no `$.ui.focus` call changes it; the underline is what keeps the real cursor readable.

## Tests

`tests/file-tree.test.ts` models a small in-memory disk (`file`, `dir`, `link`, `fifo` nodes) and answers `fs.*` and `process.run` through test-side `on(...)` hooks that sit beneath the plugin. `install(on, tree)` sets it up, `open($, cols, rows, surface)` renders the pane and returns a parsed view, and `scroll` drives `ui.scroll`. Suites: `tree`, `preview`, `ui.scroll`, `sizes`, `hooks`, then `audit`, `e2e`, `re-audit`, `round 3` and `big files` from the bug rounds, and later `round N` suites (`round 9` covers the scrollbar and Tab into the preview). Only the empty-folder and one-file cases loop over both `terminal` and `desktop` surfaces; the rest run on the terminal. The unit tests cannot show paint, hover or real clicks, and the kit has no ring of its own (a test answers `ui.focus` itself) and no implementation behind a plugin's `$.ui.scroll`, so check layout and focus changes by hand in a session: run `claude --debug-file <log>` in tmux, drive keys with `tmux send-keys` (a burst of wheel events is `send-keys -l` with several `\e[<64;col;rowM` in one write) and read presses and focus moves from the log. To cover new fs behavior, extend the `Node` model rather than stubbing inside a single test.
